# Decentralized Product Provenance & Warranty dApp

**COMP5565 group project** — an on-chain registry that records where a physical product
came from, who owns it right now, and whether its warranty is still valid.

Every unit is registered by its manufacturer. Each hand-over — manufacturer to retailer,
retailer to customer, customer to customer on resale, or back to a service centre — is
appended to an immutable **chain of custody**. The **warranty terms** (duration, claim
limit, transferability) are frozen at registration time, while the live warranty state
(claims used, expiry, voided flag) is tracked on-chain.

```
Manufacturer --> Retailer --> Customer --> (Resale) --> Customer #2
                                     \--> Service centre
```

## Quick start

All commands are run **from the repository root**. The root `package.json` is an npm
workspaces manifest, so a single `npm install` covers both workspaces.

```powershell
# 0. Install every dependency for both workspaces (one time)
npm install

# 1. Compile the Solidity sources.
#    Also generates TypeChain bindings in contracts/types/.
npm run compile

# 2. Run the contract test suite (28 tests on an in-process simulated network).
npm test

# 3. Type-check the Hardhat workspace. It compiles first, because the generated
#    TypeChain types must exist before tsc can resolve them.
npm run typecheck
```

Now bring up the local development environment. **Step 4 needs its own terminal**
because `hardhat node` blocks.

```powershell
# 4. Terminal A - local Ethereum node on http://127.0.0.1:8545 (chain id 31337)
npm run chain
```

```powershell
# 5. Terminal B - deploy the registry to that node
npm run deploy:local
#    -> ProductProvenance deployed to 0x5FbDB2315678afecb367f032d93F642f64180aa3

# 6. Refresh the frontend bindings (ABI + chainId -> address map)
npm run export:abi

# 7. Optional but recommended: seed a full demo lifecycle so the UI has data
npm run seed:local

# 8. Start the frontend
npm run dev            # -> http://localhost:3000
```

> On macOS/Linux the commands are identical; only the `Copy-Item` below becomes `cp`.

### Point MetaMask at the local chain

1. Add a network: **RPC URL** `http://127.0.0.1:8545`, **Chain ID** `31337`,
   **Currency** `ETH`.
2. Import one of the accounts that `npm run chain` printed, using its private key.
   The account printed by `npm run deploy:local` is the deployer and therefore the
   first authorised manufacturer, so it can call `registerProduct`.

### Browse without deploying

`frontend/.env.local` is optional. When `NEXT_PUBLIC_PRODUCT_PROVENANCE_ADDRESS` is
unset, the app falls back to the address recorded in
`frontend/lib/deployed-contracts.json` (written by `npm run export:abi`).

```powershell
# optional - only needed to override the generated address / chain / RPC
Copy-Item frontend/.env.local.example frontend/.env.local
```

## The smart contract

`contracts/contracts/ProductProvenance.sol` — one self-contained registry that inherits
OpenZeppelin's `Ownable`.

### Data model

| Type              | Purpose                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------ |
| `ProductModel`    | Static description: `brand`, `modelName`, `modelNumber`, `category`, `metadataURI`.                    |
| `WarrantyTerms`   | Immutable warranty contract: `durationSeconds`, `maxClaims` (0 = unlimited), `transferable`.           |
| `WarrantyState`   | Live state: `startTime`, `expirationTime`, `claimsUsed`, `voided`.                                     |
| `OwnershipRecord` | One hop: `owner`, `role`, `transferredAt`, `reason`, `evidenceHash`.                                   |
| `WarrantyClaim`   | `claimId`, `claimant`, `filedAt`, `resolvedAt`, `status`, `description`, `resolution`, `evidenceHash`. |
| `Product`         | The full record: id, serial, model, manufacturer, current owner, status, terms, state, timestamps.     |

Enums: `PartyRole` (Manufacturer / Retailer / Customer / Reseller / ServiceCenter),
`ProductStatus` (None / Registered / InTransit / Sold / Recalled), `TransferReason`
(Manufactured / Distribution / RetailSale / Resale / Return / Servicing / Recall) and
`ClaimStatus` (Pending / Approved / Rejected).

### Storage

```solidity
uint256 private _nextProductId = 1;                              // ids start at 1
mapping(uint256 => Product) private _products;
mapping(bytes32 => uint256) private _serialToProductId;          // keccak256(serial) -> id
mapping(uint256 => OwnershipRecord[]) private _ownershipHistory; // append-only
mapping(uint256 => WarrantyClaim[]) private _warrantyClaims;
mapping(address => bool) public authorizedManufacturers;
```

Arrays live in their own mappings instead of inside `Product`, so reading a product
never pays for its whole history.

### Key functions

| Function                                                                                               | Who can call it         | What it does                                                  |
| ------------------------------------------------------------------------------------------------------ | ----------------------- | ------------------------------------------------------------- |
| `setManufacturerAuthorization(address, bool)`                                                          | contract owner          | grant / revoke the right to register products                 |
| `registerProduct(serialNumber, model, terms, evidenceHash)`                                            | authorised manufacturer | creates the record, starts the warranty clock, appends hop #0 |
| `transferProductOwnership(productId, newOwner, role, reason, evidenceHash)`                            | current owner           | appends the next hop, updates `currentOwner` and `status`     |
| `fileWarrantyClaim(productId, description, evidenceHash)`                                              | current owner           | consumes one claim slot, opens a `Pending` claim              |
| `resolveWarrantyClaim(productId, claimId, approved, resolution)`                                       | authorised manufacturer | approves or rejects a claim                                   |
| `extendWarranty(productId, extraSeconds)`                                                              | the unit's manufacturer | goodwill extension of `expirationTime`                        |
| `voidWarranty(productId, reason)`                                                                      | manufacturer or owner   | invalidates the warranty                                      |
| `recallProduct(productId, reason)`                                                                     | the unit's manufacturer | marks the unit `Recalled` and voids the warranty              |
| `getProduct` / `getOwnershipHistory` / `getOwnershipRecord` / `getWarrantyClaims` / `getWarrantyClaim` | anyone                  | read-only views                                               |
| `getProductIdBySerial` / `isRegistered`                                                                | anyone                  | serial-number lookup                                          |
| `isWarrantyValid` / `remainingClaims` / `totalProducts`                                                | anyone                  | derived warranty state                                        |

### Behaviour worth knowing

- A serial number can only ever be registered once (`keccak256` of the string is the key).
- A `Resale` of a unit whose `WarrantyTerms.transferable == false` automatically voids
  the warranty. Ordinary supply-chain hops (`Distribution`, `RetailSale`) never do.
- `isWarrantyValid` returns `false` when the product is unknown, voided, recalled,
  expired, or out of claim slots.
- A recalled unit can no longer change hands.
- Reverts use **custom errors** (`ProductNotFound`, `NotProductOwner`,
  `ClaimLimitReached`, ...) so tests assert on typed errors and the frontend can
  decode them.
- Ownership of the _product_ is tracked by `transferProductOwnership`; ownership of the
  _contract_ is still `Ownable.transferOwnership`. The names are deliberately distinct
  so the ABI has no ambiguous overloads.

### Events

`ProductRegistered`, `ProductOwnershipTransferred`, `WarrantyClaimFiled`,
`WarrantyClaimResolved`, `WarrantyVoided`, `WarrantyExtended`, `ProductRecalled`,
`ManufacturerAuthorized`.

> The provenance event is deliberately _not_ called `OwnershipTransferred`:
> OpenZeppelin's `Ownable` already emits `OwnershipTransferred(address,address)`, and
> two same-named events make ethers.js / viem decoding ambiguous.

## The frontend

Next.js 15 App Router, Tailwind CSS v4, wagmi v3 + viem + TanStack Query for wallet
interaction, and ethers.js v6 helpers for everything else.

### How a contract address reaches the UI

```
npm run deploy:local
      |
      v
contracts/deployments/localhost.json        { chainId, address, ... }
      |
      |  npm run export:abi
      v
frontend/lib/abi/ProductProvenance.ts       ABI as a `const` assertion  -> viem/wagmi types
frontend/lib/abi/ProductProvenance.json     plain JSON ABI              -> ethers.js
frontend/lib/deployed-contracts.json        chainId -> address
      |
      v
frontend/lib/contracts.ts   getProductProvenanceAddress(chainId)
```

Resolution order in `getProductProvenanceAddress`:

1. `NEXT_PUBLIC_PRODUCT_PROVENANCE_ADDRESS` (from `frontend/.env.local`),
2. the generated `deployed-contracts.json` for that chain id,
3. the zero address, so the app still renders before anything is deployed.

Because the ABI is exported as a `const` assertion, `useReadContract` /
`useWriteContract` infer argument and return types from it — passing a wrong argument
type is a compile error.

### Pages

| Route       | Component                   | Purpose                                                              |
| ----------- | --------------------------- | -------------------------------------------------------------------- |
| `/`         | `app/page.tsx`              | overview + the active contract address, chain id and RPC             |
| `/register` | `register-product-form.tsx` | manufacturer registers a unit and its warranty terms                 |
| `/product`  | `product-lookup.tsx`        | serial-number lookup, chain of custody, warranty state, claim filing |

`app/providers.tsx` mounts `WagmiProvider` + `QueryClientProvider` once for the whole
app. `lib/wagmi.ts` registers two chains — Hardhat (`31337`) and Sepolia — and the
`injected` connector, with `ssr: true` so the App Router does not hit hydration
mismatches.

### ethers.js vs viem

Both are wired up on purpose:

- **viem / wagmi** drive the React UI (`useConnection`, `useReadContract`,
  `useWriteContract`, `useWaitForTransactionReceipt`).
- **ethers.js v6** is available for imperative work — see `lib/ethers.ts`:
  `getReadOnlyProvider()`, `getBrowserProvider()` and `getProvenanceContract()`.

## Testing

```powershell
npm test                 # 28 tests, in-process network, no node required
npm run coverage         # coverage report in contracts/coverage/
npm run typecheck        # Solidity compile + TypeScript check
cd frontend; npm run lint  # ESLint over the Next.js workspace
```

The suite covers registration, the full
`Manufacturer -> Retailer -> Customer -> Resale` chain, warranty transferability,
claim limits, expiry (via `networkHelpers.time.increase`), voiding, recalls,
extensions, access control and every view.

Tests use `loadFixture`, so each `it` starts from the same snapshot and stays fast
(~250 ms for the whole suite).

## Notes, conventions and next steps

**Conventions**

- Custom errors instead of revert strings; `NatSpec` comments on every external
  function and struct.
- Money-free contract, so no `ReentrancyGuard` is required yet — add one before
  introducing payments (e.g. paid warranty extensions).
- TypeScript `strict` in both workspaces. Generated files
  (`contracts/types/**`, `frontend/lib/abi/**`) are git-ignored or excluded from lint.

**Known trade-offs**

- `productId` is sequential and `serialNumber` is a plain string, so lookups are
  cheap but the string itself is not indexed off-chain. Add an indexer / subgraph if
  you need full-text search.
- `keccak256(serialNumber)` is stored, not the serial itself, for the lookup key —
  the human-readable serial still lives in the `Product` struct.
- The frontend is intentionally wallet-only (`injected`). Add WalletConnect by
  installing `@walletconnect/ethereum-provider` and registering the connector from
  `wagmi/connectors/walletConnect` (wagmi v3 makes connector dependencies optional
  peers).

**Ideas for the next iteration**

- ERC-721 / ERC-1155 representation so a product becomes a transferable token.
- IPFS pinning service for `metadataURI` and `evidenceHash` payloads.
- A manufacturer dashboard that lists all units it registered
  (`ProductRegistered` event filters).
- Role-based access control (`AccessControl` with `MANUFACTURER_ROLE`,
  `SERVICE_ROLE`) instead of the single `authorizedManufacturers` mapping.
- Subgraph / Ponder indexer plus pagination for large registries.
- Signature-based "proof of delivery" so the receiving party co-signs each hop.
