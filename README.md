# Decentralized Product Provenance & Warranty dApp

**COMP5565 group project** — an on-chain registry that records where a physical product
came from, who owns it right now, and whether its warranty is still valid.

Every unit is registered by its manufacturer. Each hand-over — manufacturer to retailer,
retailer to customer, customer to customer on resale, or back to a service centre — is
appended to an immutable **chain of custody**. The **warranty terms** (duration, claim
limit, transferability) are frozen at registration time, while the live warranty state
(claims used, expiry, voided flag) is tracked on-chain.

```
Manufacturer --> Retailer --> Customer --> (Resale) --> Customer #2
                                     \--> Service centre
```

## Quick start

All commands are run **from the repository root**. The root `package.json` is an npm
workspaces manifest, so a single `npm install` covers both workspaces.

```powershell
# 0. Install every dependency for both workspaces (one time)
npm install

# 1. Compile the Solidity sources.
#    Also generates TypeChain bindings in contracts/types/.
npm run compile

# 2. Run the contract test suite (70 tests on an in-process simulated network).
npm test

# 3. Type-check the Hardhat workspace. It compiles first, because the generated
#    TypeChain types must exist before tsc can resolve them.
npm run typecheck
```

Now bring up the local development environment. **Step 4 needs its own terminal**
because `hardhat node` blocks.

```powershell
# 4. Terminal A - local Ethereum node on http://127.0.0.1:8545 (chain id 31337)
npm run chain
```

```powershell
# 5. Terminal B - deploy the registry to that node
npm run deploy:local
#    -> ProductWarrantyRegistry deployed to 0x5FbDB2315678afecb367f032d93F642f64180aa3

# 6. Refresh the frontend bindings (ABI + chainId -> address map)
npm run export:abi

# 7. Seed the demo: grants the four supply-chain roles to the printed accounts and
#    walks a full lifecycle (register -> retailer -> customer -> claim -> servicing -> resale)
npm run seed:local

# 8. Start the frontend
npm run dev            # -> http://localhost:3000
```

> On macOS/Linux the commands are identical; only the `Copy-Item` below becomes `cp`.

### Point MetaMask at the local chain

1. Add a network: **RPC URL** `http://127.0.0.1:8545`, **Chain ID** `31337`,
   **Currency** `ETH`.
2. Import one of the accounts that `npm run chain` printed, using its private key.
   The deployer is the registry admin (`DEFAULT_ADMIN_ROLE`). `npm run seed:local`
   grants it `MANUFACTURER_ROLE` and hands the retailer / customer / service-centre
   roles to the other printed accounts, so the whole lifecycle can be clicked through.

### Browse without deploying

`frontend/.env.local` is optional. When `NEXT_PUBLIC_PRODUCT_WARRANTY_REGISTRY_ADDRESS` is
unset, the app falls back to the address recorded in
`frontend/lib/deployed-contracts.json` (written by `npm run export:abi`).

```powershell
# optional - only needed to override the generated address / chain / RPC
Copy-Item frontend/.env.local.example frontend/.env.local
```

## The smart contracts

Two complete implementations ship in `contracts/contracts/`. The frontend, the deploy
scripts and the Ignition module are wired to the **role-based** one.

| Contract                      | Access model                                          | Status                               |
| ----------------------------- | ----------------------------------------------------- | ------------------------------------ |
| `ProductWarrantyRegistry.sol` | OpenZeppelin `AccessControl`, four supply-chain roles | **deployed + bound to the frontend** |
| `ProductProvenance.sol`       | `Ownable` + an `authorizedManufacturers` mapping      | earlier iteration, still tested      |

### Roles

| Role                  | Can call                                                                |
| --------------------- | ----------------------------------------------------------------------- |
| `DEFAULT_ADMIN_ROLE`  | `grantRole` / `revokeRole` (the deployer, or whoever it promotes)        |
| `MANUFACTURER_ROLE`   | `registerProduct`, `transferToRetailer`, `voidWarranty`, `recallProduct` |
| `RETAILER_ROLE`       | `transferToCustomer` (the retail sale)                                   |
| `CUSTOMER_ROLE`       | `transferOwnership` (resale), `submitWarrantyClaim`                      |
| `SERVICE_CENTER_ROLE` | `resolveWarrantyClaim`, `logServiceAction`                               |

The constructor grants `DEFAULT_ADMIN_ROLE` only, so every other role is handed out
explicitly: `npm run seed:local` does it for the local demo accounts, and
`scripts/grant-roles.ts` for a public network.

### Data model

| Type              | Purpose                                                                                |
| ----------------- | -------------------------------------------------------------------------------------- |
| `ProductModel`    | Static description: `brand`, `modelName`, `modelNumber`, `category`, `metadataURI`.     |
| `Warranty`        | One packed slot: `startDate`, `expirationDate`, `maxClaims`, `claimCount`, `status`.    |
| `OwnershipRecord` | One hop: `from`, `to`, `toRole`, `reason`, `transferredAt`, `evidenceHash`.             |
| `WarrantyClaim`   | `claimId`, `claimant`, `filedAt`, `resolvedAt`, `status`, `description`, `resolution`.  |
| `ServiceRecord`   | `recordId`, `serviceCenter`, `loggedAt`, `action`, `evidenceHash`.                      |
| `Product`         | The full record: id, serial, model, manufacturer, `createdAt`, status, owner, warranty. |

Enums: `PartyRole` (Manufacturer / Retailer / Customer), `ProductStatus` (None /
Registered / InTransit / Sold / Recalled), `TransferReason` (Manufactured /
Distribution / RetailSale / Resale / Recall), `ClaimStatus` (Pending / Approved /
Rejected), `WarrantyStatus` (None / Active / Expired / Void) and `ExpirationReason`
(DurationElapsed / ClaimLimitReached).

### Storage

```solidity
uint256 private _nextProductId = 1;                              // ids start at 1
mapping(uint256 => Product) private _products;
mapping(bytes32 => uint256) private _serialToProductId;          // keccak256(serial) -> id
mapping(uint256 => OwnershipRecord[]) private _ownershipHistory; // append-only
mapping(uint256 => WarrantyClaim[]) private _warrantyClaims;
mapping(uint256 => ServiceRecord[]) private _serviceLog;         // "log servicing actions"
```

Arrays live in their own mappings instead of inside `Product`, so reading a product
never pays for its whole history.

### Key functions

| Function                                                                          | Who can call it        | What it does                                           |
| --------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------ |
| `registerProduct(serialNumber, model, duration, maxClaims)`                       | manufacturer           | creates the record, starts the warranty clock, hop #0    |
| `transferToRetailer(productId, retailer, evidenceHash)`                           | owner + manufacturer   | ships the unit; receiver needs `RETAILER_ROLE`           |
| `transferToCustomer(productId, customer, evidenceHash)`                           | owner + retailer       | retail sale; receiver needs `CUSTOMER_ROLE`              |
| `transferOwnership(productId, newOwner, evidenceHash)`                            | owner + customer       | resale; the remaining warranty travels with the unit     |
| `submitWarrantyClaim(productId, description)`                                     | owner + customer       | consumes a claim slot, opens a `Pending` claim           |
| `resolveWarrantyClaim(productId, claimId, approved, resolution)`                  | service centre         | approves or rejects a claim                              |
| `logServiceAction(productId, action, evidenceHash)`                               | service centre         | appends a servicing record (no claim slot consumed)      |
| `voidWarranty(productId, reason)` / `recallProduct(productId, reason)`            | manufacturer of record | invalidates the warranty / recalls and freezes the unit  |
| `syncWarrantyStatus(productId)`                                                   | anyone                 | persists an expiry that already happened                 |
| `getProduct` / `getWarranty` / `getWarrantyStatus` / `isWarrantyActive`           | anyone                 | record + derived warranty state                          |
| `getOwnershipHistory` / `getWarrantyClaims` / `getServiceLog`                     | anyone                 | the three append-only logs                               |
| `getProductIdBySerial` / `isSerialRegistered` / `totalProducts` / `remainingClaims` | anyone                 | lookups and counters                                     |

### Behaviour worth knowing

- A serial number can only ever be registered once (`keccak256` of the string is the key).
- Warranty status is **derived, never trusted**: `getWarrantyStatus` recomputes it from
  `block.timestamp` and `claimCount`, so a warranty cannot look active just because
  nobody poked the contract. `syncWarrantyStatus` (public) persists the transition and
  emits `WarrantyExpired(productId, DurationElapsed | ClaimLimitReached, expirationDate)`.
- Claim slots are consumed on **submission**, not on approval, so a rejection does not
  give the warranty a second life; `maxClaims == 0` means unlimited.
- A recalled unit can no longer change hands (`ProductIsRecalled`), and a recall voids
  the warranty.
- Voiding and recalling require the manufacturer **of record**, not merely the role.
- Reverts use **custom errors** (`ProductNotFound`, `RecipientNotAuthorized`,
  `ClaimLimitReached`, `AccessControlUnauthorizedAccount`, ...) so tests assert on typed
  errors and the frontend can decode them.
- The contract is money-free (no `payable` function, no ETH), so there is no reentrancy
  surface; add a guard before introducing payments such as paid extensions.

### Events

`ProductRegistered`, `WarrantyCreated`, `ProductOwnershipTransferred`,
`WarrantyClaimSubmitted`, `WarrantyClaimResolved`, `ServiceActionLogged`,
`WarrantyExpired`, `WarrantyVoided`, `ProductRecalled`, plus OpenZeppelin's
`RoleGranted` / `RoleRevoked`.

> The custody event is deliberately _not_ called `OwnershipTransferred`: contracts that
> inherit OpenZeppelin's `Ownable` already emit that signature, and two same-named
> events make ethers.js / viem decoding ambiguous.

## The frontend

Next.js 15 App Router, Tailwind CSS v4, wagmi v3 + viem + TanStack Query for wallet
interaction, and ethers.js v6 helpers for everything else.

Six routes, one per job a role has to do; every write path is role-gated in the UI *and*
in the contract - see the page table under [Pages](#pages).

### How a contract address reaches the UI

```
npm run deploy:local
      |
      v
contracts/deployments/localhost.json        { chainId, address, ... }
      |
      |  npm run export:abi
      v
frontend/lib/abi/ProductWarrantyRegistry.ts   ABI as a `const` assertion  -> viem/wagmi types
frontend/lib/abi/ProductWarrantyRegistry.json plain JSON ABI              -> ethers.js
frontend/lib/deployed-contracts.json          chainId -> address
      |
      v
frontend/lib/contracts.ts   getRegistryAddress(chainId)
```

Resolution order in `getRegistryAddress`:

1. `NEXT_PUBLIC_PRODUCT_WARRANTY_REGISTRY_ADDRESS` (from `frontend/.env.local`; the old
   `NEXT_PUBLIC_PRODUCT_PROVENANCE_ADDRESS` name still works as an alias),
2. the generated `deployed-contracts.json` for that chain id,
3. the zero address, so the app still renders before anything is deployed.

Because the ABI is exported as a `const` assertion, `useReadContract` /
`useWriteContract` infer argument and return types from it — passing a wrong argument
type is a compile error.

### Pages

| Route       | Component                 | Purpose                                                                        |
| ----------- | ------------------------- | ------------------------------------------------------------------------------ |
| `/`         | `app/page.tsx`            | overview, role map, active contract address, chain id and RPC                  |
| `/register` | `register-product-form`   | manufacturer registers a unit and freezes its warranty terms                   |
| `/product`  | `product-lookup`          | serial lookup, chain of custody, warranty state, claims, servicing log, claim filing |
| `/transfer` | `transfer-panel`          | typed hand-overs: `transferToRetailer` / `transferToCustomer` / `transferOwnership` |
| `/service`  | `service-console`         | service centre: resolve pending claims + `logServiceAction`                     |
| `/manage`   | `manufacturer-console`    | "my units" dashboard, `voidWarranty`, `recallProduct`, `syncWarrantyStatus`     |

`lib/use-registry.ts` holds the shared wagmi hooks (`useRoles`, `useProductList`,
`useProductDetail`, `useRegistryWrite`); `components/ui.tsx` holds the shared cards,
fields, status chips and transaction feedback, so the four role screens behave
identically. `useRegistryWrite` invalidates every cached read after a confirmation, which
is what keeps the open dashboards in sync after a transfer.

`app/providers.tsx` mounts `WagmiProvider` + `QueryClientProvider` once for the whole
app. `lib/wagmi.ts` registers two chains — Hardhat (`31337`) and Sepolia — and the
`injected` connector, with `ssr: true` so the App Router does not hit hydration
mismatches.

### ethers.js vs viem

Both are wired up on purpose:

- **viem / wagmi** drive the React UI (`useConnection`, `useReadContract`,
  `useWriteContract`, `useWaitForTransactionReceipt`).
- **ethers.js v6** is available for imperative work — see `lib/ethers.ts`:
  `getReadOnlyProvider()`, `getBrowserProvider()` and `getRegistryContract()`.

## Deploying to Sepolia

```powershell
# 1. configure the credentials and the role holders (see above)
Copy-Item contracts/.env.example contracts/.env
# ... edit contracts/.env, then:

# 2. deploy (the deployer becomes DEFAULT_ADMIN_ROLE)
npm run deploy:sepolia

# 3. grant the supply-chain roles to the demo / team accounts
cd contracts
npx hardhat run scripts/grant-roles.ts --network sepolia
cd ..

# 4. publish the new address + ABI to the frontend
npm run export:abi

# 5. point the UI at Sepolia
#    frontend/.env.local -> NEXT_PUBLIC_CHAIN_ID=11155111
npm run dev
```

The constructor only grants `DEFAULT_ADMIN_ROLE`, so **skipping step 3 leaves every
action disabled** in the UI (`registerProduct`, both transfers, claims, servicing). The
addresses to grant are read from `contracts/.env`:

```dotenv
MANUFACTURER_ADDRESSES=0xabc...,0xdef...
RETAILER_ADDRESSES=0xabc...
CUSTOMER_ADDRESSES=0xabc...,0xdef...
SERVICE_CENTER_ADDRESSES=0xabc...
```

Verify the source on Etherscan once deployed (`initialAdmin` is the constructor argument,
i.e. the deployer address):

```powershell
cd contracts
npx hardhat verify --network sepolia <DEPLOYED_ADDRESS> <INITIAL_ADMIN_ADDRESS>
```

## Notes, conventions and next steps

**Conventions**

- Custom errors instead of revert strings; `NatSpec` comments on every external
  function and struct.
- Money-free contract, so no `ReentrancyGuard` is required yet — add one before
  introducing payments (e.g. paid warranty extensions).
- TypeScript `strict` in both workspaces. `contracts/types/**` (TypeChain) is git-ignored
  because `npm run compile` recreates it, while `frontend/lib/abi/**` and
  `frontend/lib/deployed-contracts.json` *are* committed — `npm run export:abi` overwrites
  them, but shipping them means a fresh clone can `npm install && npm run dev` (or
  `npm run build`) without deploying anything first. Both are excluded from Prettier and
  ESLint as machine-owned.
- Prettier runs with `endOfLine: "auto"`, so Windows (CRLF) and macOS/Linux (LF) checkouts
  both pass `npm run format:check`.

**Known trade-offs**

- `productId` is sequential and `serialNumber` is a plain string, so lookups are
  cheap but the string itself is not indexed off-chain. Add an indexer / subgraph if
  you need full-text search.
- `keccak256(serialNumber)` is stored, not the serial itself, for the lookup key —
  the human-readable serial still lives in the `Product` struct.
- The frontend is intentionally wallet-only (`injected`). Add WalletConnect by
  installing `@walletconnect/ethereum-provider` and registering the connector from
  `wagmi/connectors/walletConnect` (wagmi v3 makes connector dependencies optional
  peers).

**Ideas for the next iteration**

- ERC-721 / ERC-1155 representation so a product becomes a transferable token.
- IPFS pinning service for `metadataURI` and `evidenceHash` payloads.
- A manufacturer dashboard that lists all units it registered
  (`ProductRegistered` event filters).
- Subgraph / Ponder indexer plus pagination for large registries.
- Signature-based "proof of delivery" so the receiving party co-signs each hop.
